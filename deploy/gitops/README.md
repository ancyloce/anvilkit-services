# GitOps and the deployment lock (P23)

The parent owns each environment's pinned combination: which chart at which version, which image digest and which environment values every component gets, and in which order Argo CD synchronizes them ([release pipeline](../../docs/architecture/platform.md#operations), step 5). Service charts stay in their service repositories.

| Path | Purpose |
| --- | --- |
| `lock.yaml` | Deployment lock and capacity worksheet: replica, autoscaling, disruption, placement and connection-pool limits of all eight services and every DD-10 platform component, per environment. Production fields are `REQUIRED` until ENV-01..05/09 exist; `tools/check-deployment-lock.py --self-test` (the `deployment` step of `tools/run-verification.py`) checks the qualification environment against it. |
| `environment/` | The `anvilkit-environment` chart: one Argo CD `AppProject` and one `Application` per component, ordered by sync wave (platform dependencies, stateful services, migrations, applications, probes). The root Application waits for each wave to be Healthy, so a failed wave stops the later ones. |
| `environments/<environment>.yaml` | An environment's combination; references to release artifacts are resolved at publication. Only `qualification` exists (DEVELOPMENT_ONLY, `development: true`). |
| `publish.py` | Refuses a release manifest that is not publishable (status, findings, dirty or unverified artifacts); mirrors the pinned upstream charts, publishes the parent's platform charts and the resolved environment chart with per-run versions into the environment's registry, signs and verifies each, and writes the root Application. `--self-test` proves the gate. |

Every source Argo CD synchronizes is a versioned, signed OCI chart; nothing is read from a branch. Argo CD does not verify Cosign signatures on Helm charts itself: `publish.py` verifies them before publishing (an already published chart again before it is reused), and the cluster's admission policy verifies every application image. The qualification registry is the development foundation's CNCF Distribution registry, not Harbor (lock: `registry` NOT_RUN).

## Release, promotion and rollback (P3.2)

- **Release.** A tag `v*` on the parent runs `.github/workflows/release.yml`: `tools/release-artifacts.py` builds every owned image from the tagged commit (submodules at their gitlinks) with BuildKit provenance, scans it (a fixable CRITICAL or HIGH finding blocks), attests an SPDX SBOM, signs keylessly with the workflow's OIDC identity (transparency log) and pushes by digest to the registry of the repository variable `ANVILKIT_RELEASE_REGISTRY`. The manifest's status is derived: `SIGNED` only for a clean, tagged, provenance-bearing, keylessly (or KMS-) signed build on a TLS registry; `BLOCKED` on any finding (a dirty input included); `SIGNED_DEVELOPMENT_ONLY` for the local development placement (the key under `.local/release`, plain HTTP, no transparency log). A `SIGNED` manifest is attached to the tag's GitHub release.
- **Publication gate.** `publish.py` publishes nothing from a manifest with findings or a status other than `SIGNED`; a combination with `development: true` (only `qualification`) also accepts `SIGNED_DEVELOPMENT_ONLY`. Every image and chart it takes must be verified and built from a clean source.
- **Promotion.** A production combination names its release: `release: {run: <tag>, manifestSha256: sha256:...}`. Promotion is a reviewed change of that field merged to `main`; `.github/workflows/promote.yml` fetches the named manifest from the tag's release, checks its digest and runs `publish.py`, which publishes the environment chart as a new version. The environment's operator points the root Application (`root-application.yaml` in the run's evidence) at it.
- **Rollback.** Reverting the promotion's change publishes the previous release again as a new environment chart version; Argo CD converges to its digests. Automated prune/self-heal are on only for a development combination or one that declares `automation.rollbackWindow`; otherwise a production environment syncs on the operator's command. `deploy/qualification/rollback-drill.py --from N --to N+1` exercises both directions on the qualification cluster (it changes workloads: the environment operator's authorization is required).
- **Scope.** The AppProject admits only the combination's application namespaces and the cluster-scoped kinds it lists (`clusterResources`, required outside development). Upstream charts whose entry declares `verify` (a cosign identity or a Helm provenance keyring) are verified before mirroring; a production combination refuses an unverified upstream chart.
- **Admission.** `deploy/qualification/platform/admission` enforces release-signed, digest-pinned images in the namespaces it lists (default `anvilkit-apps`, `anvilkit-platform`, `anvilkit-data`, `anvilkit-observability`) with the transparency log verified; ignoring the log or a plain-HTTP registry renders only with `development: true` (qualification, which also enforces `anvilkit-apps` alone until its platform images are mirrored and signed).

```sh
.local/verification-venv/bin/python tools/release-artifacts.py --run RUN
.local/verification-venv/bin/python deploy/gitops/publish.py --environment qualification --run RUN
.local/verification-venv/bin/python deploy/qualification/bootstrap.py --run RUN
```
