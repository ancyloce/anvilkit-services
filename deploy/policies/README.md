# Policies of the trusted Job boundary (P09)

Reviewed admission, syscall and network policies of the `anvilkit-components` namespace (DD-03 §4–§5, DD-10 §4, SEC-09). They constrain what the launcher's fixed templates may look like; they are not a general admission platform.

| Path | What it is | Where it applies |
|---|---|---|
| `chart/templates/components-jobs.yaml` | Kyverno 1.19 `ValidatingPolicy` (CEL) for Pods and Jobs: the launcher's labels and create-request marker, the fixture layout (`fixture`, no init container) or the harness layout (the `supervisor` container plus `access-sidecar` as a native sidecar, an init container with `restartPolicy: Always`) and nothing else, the profile id bound to the layout, the candidate-code label and the RuntimeClass (`local-check-v1`: fixture, no candidate code, no RuntimeClass; `harness-wiring-dev-v1`: harness, no candidate code, no RuntimeClass; `codegen-fixed-v1`: harness, candidate code, `gvisor`; nothing else), images pinned to the qualified digests of `contracts/jobs/profiles.json`, the fixture command pinned to the reviewed `local-check-v1` entrypoint verbatim, no arguments/envFrom/ports, no lifecycle hook or liveness/readiness/startup probe on any container, an exact environment per container with the Pod UID from the downward API, only emptyDir volumes plus the access sidecar's identity Secret (`anvilkit-job-access-sidecar-identity`, P0.1, read-only at `/etc/anvilkit/identity` in the sidecar alone, required in the harness layout), exact mounts without subPath/subPathExpr/mountPropagation/recursiveReadOnly, all capabilities dropped with the supervisor's SETUID/SETGID/SETPCAP as the only addition (bound to the qualified entrypoint and UID 0), the candidate syscall profile on the supervisor, RuntimeDefault on the sidecar, UID 10002 for the sidecar, no token/host namespace/shared PID, the components node pool, no launcher-supplied nodeName (scheduled Pod updates remain valid), the default scheduler only, exact supervisor/native-sidecar requests and limits and emptyDir sizeLimit/medium settings, gVisor for candidate code; Jobs with one Pod once, no retries, an absolute deadline, no TTL. Delivery (P0.5): the policies, the registry allowlist and the seccomp installer are the Helm chart `chart/` (`anvilkit-job-admission`), installed by `deploy/dev/up.sh` into the development cluster and by the qualification combination (`deploy/gitops/environments/qualification.yaml`, after Kyverno, whose admission controller runs three replicas behind a PDB); `deploy/qualification/bootstrap.py` runs `check.sh --cluster` against the qualification cluster after the sync, with the launcher's own short-lived token, and records it under `outputs/qualification/<run>/admission/`.

Records: offline evaluation and cluster admission are two different results and are reported separately (delivery.md, P09 record). A Pod NetworkPolicy isolates Pods, not the two containers of one Pod: the syscall profile is what keeps the candidate off the network on the runc path, and the gVisor combination (G-04/G-05) is qualified separately.

The F1/F2 mutations cover both Pods and Job templates. Job requests use the real launcher
identity. The current reviewed harness values are supervisor `500m/256Mi` (validator
`1/1Gi`) and sidecar `100m/64Mi`, equal requests and limits; workspace `1Gi` and verdict
`256Mi` use disk, sockets `1Mi` uses `Memory`. Kubernetes can restore an omitted request
from its corresponding limit; the admitted values must still equal the reviewed values.

The validator profiles (P0.8) use the harness layout with the `anvilkit-validator` image as
the supervisor container, bound to the image's pinned digest and to its reviewed entrypoint
(`node /anvilkit/validator/dist/job.js`). `validator-fixture-v1` validates only the fixed
Hero source without candidate code or RuntimeClass; `validator-source-v1` binds a candidate
source revision (`bindsSource`) and runs it as candidate code under gVisor;
`validator-source-dev-v1` is the same without a RuntimeClass and is admitted only where the
chart's `developmentProfiles` lists it (the dev values do, qualification does not). The
policy refuses the codegen supervisor's command or image under a validator profile, the
validator's under a codegen profile, an extended command, the fixture profile relabeled as
candidate code or given a RuntimeClass, the source profile without gVisor and the
development profile in an environment that does not list it (`mutate.py`, `validator-*`
cases).
No quota manager or scheduler is added.

`check.sh --cluster` also creates one disposable harness Job, observes normal scheduler
binding, updates the scheduled Pod, then calls the actual `pods/ephemeralcontainers`
UPDATE endpoint. The launcher must receive an RBAC denial and the administrator must
receive the dedicated policy denial. The old CREATE-with-ephemeralContainers mutation is
reported as API structural rejection, not evidence for that subresource policy. Only the
probe's own Job is deleted. Candidate Pod admission remains UNEXECUTED without the gVisor
RuntimeClass. See the [P09 repair record](../../docs/architecture/delivery.md#verification-p09-repair)
for image revisions, results and target-runtime blockers.

The parser policies (P15, P0.7) are proven by this suite too: `check.sh` renders the
parser Job and Pod exactly as Knowledge's launcher does (`services/agent/knowledge`
`test/parse.test.ts` with `ANVILKIT_RENDER_POLICY_FIXTURES`), `tests/mutate.py` derives the
parser cases (the stagers' and the parser's `/tmp` shared, a writable input or result, missing
resources, an unbounded or in-memory emptyDir, no node pool, a ServiceAccount, an unconfined
stager, a working directory, a `PYTHONPATH`, a foreign digest, a deadline above one hour), and
`--cluster` submits the parser Jobs with Knowledge's launcher kubeconfig
(`ANVILKIT_PARSER_LAUNCHER_KUBECONFIG`, default `.local/dev/knowledge-launcher.kubeconfig`).
`TestIngestion` (tests/integration) additionally runs the launcher's real Jobs through the
admission chain and submits tampered ones with the launcher's own kubeconfig.
