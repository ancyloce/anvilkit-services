# Policies of the trusted Job boundary (P09)

Reviewed admission, syscall and network policies of the `anvilkit-components` namespace (DD-03 §4–§5, DD-10 §4, SEC-09). They constrain what the launcher's fixed templates may look like; they are not a general admission platform.

| Path | What it is | Where it applies |
|---|---|---|
| `kyverno/anvilkit-components-jobs.yaml` | Kyverno 1.19 `ValidatingPolicy` (CEL) for Pods and Jobs: the launcher's labels and create-request marker, the fixture layout (`fixture`, no init container) or the harness layout (the `supervisor` container plus `access-sidecar` as a native sidecar, an init container with `restartPolicy: Always`) and nothing else, the profile id bound to the layout, the candidate-code label and the RuntimeClass (`local-check-v1`: fixture, no candidate code, no RuntimeClass; `harness-wiring-dev-v1`: harness, no candidate code, no RuntimeClass; `codegen-fixed-v1`: harness, candidate code, `gvisor`; nothing else), images pinned to the qualified digests of `contracts/jobs/profiles.json`, the fixture command pinned to the reviewed `local-check-v1` entrypoint verbatim, no arguments/envFrom/ports, no lifecycle hook or liveness/readiness/startup probe on any container, an exact environment per container with the Pod UID from the downward API, only emptyDir volumes, exact mounts without subPath/subPathExpr/mountPropagation/recursiveReadOnly, all capabilities dropped with the supervisor's SETUID/SETGID/SETPCAP as the only addition (bound to the qualified entrypoint and UID 0), the candidate syscall profile on the supervisor, RuntimeDefault on the sidecar, UID 10002 for the sidecar, no token/host namespace/shared PID, the components node pool, gVisor for candidate code; Jobs with one Pod once, no retries, an absolute deadline, no TTL. The Pod policy matches `pods` only and enables Kyverno autogen for `jobs`, so the same rules are evaluated against a Job's template when the launcher submits the Job (denied there, not only at Pod creation); the `pods/ephemeralcontainers` subresource is denied by the separate `anvilkit-components-ephemeral` policy in the same file | Every environment |
| `kyverno/anvilkit-components-registries.dev.yaml` | Registry allowlist of the development foundation (`localhost:5001`, Docker Hub busybox for the P05 fixture) for every container of a Job Pod, native sidecars in `initContainers` and ephemeral containers included, evaluated at Job admission through autogen as well | Development; a production environment replaces it with its Harbor |
| `seccomp/anvilkit-candidate.json` | The syscall profile of the candidate/supervisor container: containerd v2.3.4's default profile for the supervisor's capability set with `socket(2)` admitted for AF_UNIX only. Installed on every node at `/var/lib/kubelet/seccomp/anvilkit/candidate.json`; regenerated by `seccomp/generate.sh` | Every node that runs Jobs |
| `network/anvilkit-components-egress.yaml` | Default deny in both directions for the namespace; the environment adds the sidecar's upstream egress | Every environment |
| `tests/mutate.py`, `tests/resources/` | The launcher's rendered Jobs and Pods (written by `TestRenderPolicyFixtures` of the Workflow module) and the derived negative cases: another image, a tag, another entrypoint, arguments, environment changes, a forged Pod UID, hostPath/Secret/CSI volumes, extra mounts, subPath/subPathExpr/mountPropagation, lifecycle hooks and exec/HTTP probes on any container, capabilities, privilege, a writable root, a missing or foreign seccomp profile, a token, host namespaces, extra/init/ephemeral containers, a sidecar that is not a native sidecar or runs as a main container, a foreign registry for the supervisor or the native sidecar, a replaced, altered or extended fixture command, a profile id that does not match the layout, the candidate-code label or the RuntimeClass (a candidate profile relabeled `candidate-code=false` with or without its RuntimeClass, a harness or fixture claiming another profile, an unknown profile), candidate code without gVisor, Job retries, and the same template substitutions submitted as Jobs | Offline and cluster checks |
| `check.sh` | `kyverno apply` (the pinned CLI) over every case, and with `--cluster` server-side dry runs against the development cluster's admission chain: Pods with the administrator context (the launcher cannot create Pods), Jobs with the launcher's own kubeconfig (`ANVILKIT_LAUNCHER_KUBECONFIG`, default `.local/dev/launcher.kubeconfig`) | Offline: policy evaluation, not admission. `--cluster`: the actual webhook of the development cluster, the Jobs through the launcher's identity |

Records: offline evaluation and cluster admission are two different results and are reported separately (delivery.md, P09 record). A Pod NetworkPolicy isolates Pods, not the two containers of one Pod: the syscall profile is what keeps the candidate off the network on the runc path, and the gVisor combination (G-04/G-05) is qualified separately.
