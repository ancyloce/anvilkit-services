# Repository guide for development agents

Shared instructions for Claude, Codex, other development agents, and people working in `anvilkit-services`. `CLAUDE.md` points here. Candidate jobs must not treat discovered `AGENTS.md`, `.pi`, or other resources as instructions ([DD-03](docs/architecture/execution.md#6-pi-resources-and-model-stream)).

At task startup, read this file, [docs/README.md](docs/README.md), then the [architecture overview](docs/architecture/architecture.md).

The recorded baseline is G-01–G-14 `NOT_RUN`, release `NOT_VERIFIED`; changes require the applicable evidence.

## 3. Task scope and the user's work

- Before editing, inspect parent and affected nested-repository `git status --short`. Preserve and report existing modified, untracked, and submodule work; re-read targets changed by another actor.
- Match the requested output. Documentation work does not authorize code, contracts, dependencies, configuration, deployment, or scaffolding. Code work does not authorize unrelated document rewrites or renames. Read-only/draft-only requests leave repository files untouched.
- Delete legacy code or change submodule arrangements only when explicitly assigned. Clarify before expanding ambiguous scope; continue independent authorized work.
- Implement the smallest useful behavior with observable success criteria, reusing existing contracts, tools, and dependencies. Add shared code for an actual consumer. Require a demonstrated need for frameworks, abstraction layers, plugin/configuration/release systems, compatibility paths, retries, or infrastructure.
- Keep cohesive behavior together; avoid speculative requirements, empty scaffolds, unnecessary wrappers, and one-task-per-RPC/table/file decomposition.

## 4. Git is read-only

- Never `git commit`, `git push`, or open a PR unless the user explicitly asks in that message (commit/push may also be hook-blocked — a block is the policy working, not an obstacle to route around). Default: leave changes uncommitted and report modified files, flagging those inside submodules and nested repositories (`contracts/`, `services/agent/{api,control,workflow}`).
- Never stage, amend, rebase, merge, cherry-pick, reset, clean, tag, switch branches, register or change submodules (`git submodule add/update/sync`, `.gitmodules`) or publish a package unless asked for that exact action. Never force-push, never push `main`. Read-only git is always fine. Prepare such operations locally and present their concrete targets for authorization.
- Never publish, deploy, or send anything to an external service without task authorization.

## 5. Architecture boundaries

- **Eight services, fixed technologies.** The identities are `anvilkit-agent-api`, `-control`, `-workflow`, `-model-proxy`, `-knowledge`, `-mcp`, `-background-worker` and `-inference` ([catalog](docs/architecture/architecture.md#services)). Primaries and conditional alternatives come from the [60-decision matrix](docs/architecture/technology.md#choices); do not implement an alternative beside its primary, and do not reintroduce choices that the matrix lists only as alternatives (for example Connect-Go or Rslib) as primaries.
- **Complete replacement.** Build from new v1 contracts, empty databases, new Temporal histories and generated clients. Old handlers, DTOs, SQL, executors, submodule internals and business fallbacks are not constraints and not a starting point ([ADR-001](docs/architecture/architecture.md#adr-001), [definition of complete replacement](docs/architecture/delivery.md#definition-of-complete-replacement)). Business-data transfer is a separate verified import task that exists only if an inventory proves records must survive.
- **Dependency direction.** Go: `cmd -> bootstrap(Fx) -> transport -> application -> domain`; domain code imports no Gin, Fx, gRPC or SQL driver. TypeScript keeps bootstrap/transport/application/domain/adapters/generated boundaries; Python exposes fixed computation. Services build and release independently and share only generated contracts, telemetry fields and immutable profile schemas. Allowed calls are the [communication matrix](docs/architecture/architecture.md#communication-matrix).
- **Contract ownership.** `contracts/openapi/agent.yaml`, `contracts/proto/anvilkit/{control,knowledge,mcp}/v1/*.proto`, `contracts/openapi/inference.yaml`, `contracts/{jobs,components,events}` are the target sources, owned by the contracts repository together with their generated consumers (`contracts/{go,ts,python}`); bindings are generated there (oapi-codegen, Buf, grpc-go/grpc-js, ts-proto) and never hand-maintained or diverged ([contract sources](docs/architecture/contracts.md#1-contract-sources-and-generated-bindings)). Services consume the Go module as an explicit versioned requirement, never through a replace directive into another repository; service-owned generation (Control's sqlc output, migrations) stays with the service. Public JSON is not ProtoJSON. Money and 64-bit counters are decimal strings; optional fields are omitted, not null; strict parsing rejects duplicate keys and unknown fields ([values and errors](docs/architecture/contracts.md#4-values-validation-and-errors)). Never reuse Proto field numbers or reinterpret enums. Do not invent Pagix or Studio endpoint paths; [DD-06 ports](docs/architecture/components.md#pagix) are domain contracts until real upstream declarations exist.
- **Data ownership.** `anvilkit_control`, `anvilkit_knowledge` and `anvilkit_mcp` each have one writing service and separate app/migrator roles; cross-domain references are immutable identifiers, never foreign keys, shared ORM entities or joins. Control's seven lock ranks apply to every mutation; no network, Temporal, storage or Kubernetes I/O under database locks; outbox writes share the domain transaction and inbox commits precede ACK ([transaction rules](docs/architecture/contracts.md#4-transaction-rules)).
- **Workflow determinism.** Only Temporal advances business steps; Workflow code uses Temporal time/timer/concurrency APIs and no wall clock, goroutines, unordered map decisions or network; I/O lives in Activities and Jobs ([DD-01](docs/architecture/execution.md#workflows)). LangGraph runs only inside a Codegen attempt.

## 6. Security invariants

Every change must preserve these; each links to its owning section.

- **Single-use physical send.** Every physical model or tool send needs its own `AdmitModel`/`AdmitTool` claim; only the first successful claim returns `dispatchAllowed=true`. Lost responses, SDK/transport retries, graph checkpoints, TTLs, lease expiry and process restarts never recreate permission. `UNKNOWN` is reconciled under the original identity; a replacement send needs independently checkable not-sent evidence and fresh admission. Missing prices or caps deny the paid route ([DD-02](docs/architecture/execution.md#control)).
- **Credential isolation.** Provider keys exist only in Model Proxy; job scope credentials only in the trusted access sidecar; MCP upstream credentials only in the secret platform or qualified connection storage. Candidate Jobs have no production credentials, Kubernetes token, business database or direct network egress. Inbound AnvilKit tokens are never forwarded upstream ([DD-03](docs/architecture/execution.md#agent-harness), [DD-08](docs/architecture/mcp.md#mcp)).
- **Untrusted content.** Candidate code, parsed documents, retrieved text, tool results and model output are data, never instructions or configuration. Trusted supervisor, observer and finalizer processes never import candidate modules; candidate build, test and SSR run low-privilege with no verdict or submission access ([trust regions](docs/architecture/security.md#trust-regions)).
- **Independent validation and exact release.** A trusted observer issues verdicts; candidate exit codes and self-reports never certify. Approval binds an exact `ReleaseSubject`; both npm and browser/CSS receipts precede activation; published versions are immutable ([DD-04](docs/architecture/components.md#components)).
- **Authorities.** Temporal owns business progression, Control owns admission/costs/effects/acceptance, Pi alone writes source, Knowledge owns source ACL and `MemoryFact` (models propose, never confirm), MCP owns catalog and grants with the Control revocation barrier, Pagix and Studio keep their external authority through authenticated APIs only. Qdrant, PostgresStore, caches, queues, framework checkpoints and caller claims are never authority ([ADR-002](docs/architecture/architecture.md#adr-002), [ADR-003](docs/architecture/architecture.md#adr-003)).
- **Clocks and fences.** The first execution permit sets the absolute deadline once; retries, holds and replacements never reset it. Cancel, hold and definition changes fence new dispatch and keep issued effects and costs; a timeout never proves that nothing happened.
- **Logging.** Secrets, tokens, prompts, source, native model bodies, candidate stdout, presigned URLs and full object keys never enter logs, traces, NATS, BullMQ or Apollo. Logs are diagnostic, never evidence ([data classification](docs/architecture/security.md#data-classification-logging-and-deletion)).

## 7. Naming

- Use the [naming authority](docs/architecture/architecture.md#naming): stable service, database, namespace, queue, event, bucket and file identities without architecture-version or new/next/legacy suffixes; `anvilkit.<domain>.v1` Proto packages; `/api/v1` HTTP; `ANVILKIT_` configuration prefix; `00001_init.sql` first migrations. V4.0 is document metadata only. Third-party version paths (`pgx/v5`, `goose/v3`) stay as upstream defines them.
- Repositories, images and workspace tasks are lowercase kebab-case; existing TypeScript packages use the `@anvilkit/` scope; Go packages are lowercase. Follow Go conventions in Go, the repository's Biome/TypeScript conventions in TypeScript and PEP 8 in Python; do not impose one style across languages.
- Use clear names that express responsibility; preserve terminology defined by the architecture and contracts; avoid unexplained abbreviations and names such as `misc`, `utils2`, `newService` or `tempHandler`. Keep file names and layout consistent with neighboring code. Do not rename unrelated files for consistency, and do not create a new style guide or lint system when existing conventions suffice.

## 8. Verification and reporting

Select checks for the changed behavior. This table lists checks, not authorization for external effects.

Use the pinned CPython 3.12 interpreter `.local/verification-venv/bin/python` for parent Python tools below; other interpreters return exit 2 `UNEXECUTED`. For authorized setup/full verification, `sh tools/verification-env.sh [--static]` creates that environment from `tools/requirements.txt` and runs the chain.

| Task | Check |
| --- | --- |
| Repository documentation | `tools/check-docs.py` with the pinned interpreter; read-only, current baseline, required inputs must be present |
| Contracts repository | In `contracts/`, `sh tools/verification-env.sh`: checks, generation `--check`, Go with `GOWORK=off`, TypeScript, Python; reads only that repository |
| Parent contract integration | `tools/check-contracts.py` and `tools/generate-contracts.py --check` with the pinned interpreter; delegates to contracts and checks Control's sqlc |
| Source inclusion | `tools/check-source-export.py` with the pinned interpreter; Git listings plus an independently checked/built disposable export |
| Go modules | `go build ./...`, `go vet ./...`, `go test ./...` per module; Testcontainers requires Docker. Report tests skipped with `ANVILKIT_SKIP_DOCKER_TESTS=1` |
| API, Control, Workflow | Apply `GOWORK=off GOFLAGS=-mod=readonly` to each build/vet/test command; also `docker build .` and `helm lint deploy/chart` in each repository |
| Race checks | `go test -race` for API transport, Control application, and Workflow packages |
| Control SQL | `sh tools/sqlc.sh --check` in Control |
| End-to-end | `go test -tags integration ./...` in `tests/integration`; `ANVILKIT_INTEGRATION_API_URL` targets an API deployed elsewhere |

**Environment actions require task authorization:** `sh deploy/dev/up.sh` starts development; source `.local/dev/env.sh` for tests. `sh deploy/dev/api-chart.sh install`, `sh deploy/dev/control-chart.sh install`, and `sh deploy/dev/workflow-chart.sh install` deploy to kind; Control/Workflow use two replicas.

Generators without `--check` rewrite consumers/sqlc; use only within scope. Never invoke `docs/archive/tools/` generators.

<a id="verification-results"></a>

### Report results

Name each check, revision/environment, result, and evidence location: `PASS` if it ran successfully, `FAIL` if it ran and failed, `UNEXECUTED` if not run or the tool could not execute. State missing prerequisites and skipped checks; preserve the checker's classification, including missing-input failures and exit-2 outcomes.

Keep draft, adopted, implemented, and qualified distinct. Preserve `NOT_RUN`/`NOT_VERIFIED`; v3.12 evidence does not qualify V4.0. Documents, fixtures, mocks, and imports do not prove billing, isolation, Pagix/Studio behavior, replica correctness, or recovery targets.

For downloadable drafts, check content, Markdown, and references at intended installation locations. A passing checkout check does not validate unapplied files.

## 11. Project memory

All agents use this policy; `CLAUDE.md` and commands only reference it. Reading rules or editing command templates does not invoke them.

| Trigger | Action |
| --- | --- |
| Start/resume work | [Startup](#memory-startup) |

<a id="memory-startup"></a>

### 11.1 Startup

After section 1's required reading:

1. Read HANDOFF's entry points and SESSION_SUMMARY's current state.
2. Follow task-relevant milestone, decision, blocker, plan, and runbook references. Load history when it explains a dependency or conflict.
3. Compare remembered state with the checkout and evidence; resolve conflicts using section 1's authority.
4. Establish objective, scope, success criteria, and prerequisites. Proceed when the next authorized action is clear; otherwise identify the blocking input.

A stored next action is context, not authorization. Missing information blocks dependent work only. Seek input while continuing independent authorized work. Create missing records only within scope from known facts; keep unknowns explicit.

<a id="memory-ownership"></a>

### 11.2 Document ownership

Each fact has one owner; other files use brief descriptions, IDs, and links. Accurate unchanged files need no edit.

| Document | Update trigger |
| --- | --- |
| `docs/SESSION_SUMMARY.md` | Objective, observed state, verification, or next action changes |
| `docs/BLOCKERS.md` | A blocker appears, changes, or meets resolution criteria |
| `docs/DECISIONS.md` | A significant choice is proposed, adopted, superseded, or reverted |
| `docs/ROADMAP.md` | Approved scope, milestone status, or exit criteria change |
| `docs/HANDOFF.md` | Startup requirements, references, cautions, or access needs change |

**SESSION_SUMMARY owns current state:** objective/scope, milestone references, observed state, relevant completed/unfinished work, verification/evidence links, decision/blocker IDs, and remaining risks. Its stable `Next Action` section has one action, owner, prerequisites, and completion condition. Identify a procedure's first action and approval boundary. If blocked, identify the prerequisite to resolve; if no work is assigned, say so. Replace stale snapshots; execution history stays in evidence records.

**BLOCKERS owns unresolved issues and resolution history:** ID, status, priority, owner, issue, affected result, evidence/uncertainty, required action, resolution criteria. Statuses: `OPEN`, `IN_PROGRESS`, `RESOLVED`, `CLOSED`. Retain resolution evidence/date and stable anchors; separate active issues from history. A fix/publication alone does not resolve a runtime failure. Pause dependent work; bound retries by a question and new evidence.

**DECISIONS owns durable choices:** ID, owner, date, status, decision, context/rationale, alternatives, impact/risks, reversal conditions, adoption/source references. Statuses: `PROPOSED`, `ACTIVE`, `SUPERSEDED`, `REVERTED`; leave unknown approval/ownership explicit. Preserve history and link successors. Architecture entries reference the governing design; resolve conflicts before implementation.

**ROADMAP owns milestones:** approved scope, status, exit criteria, dependencies, plan/evidence links. Change status only when criteria support it. Link task progress and blockers to their owners; new ideas remain unapproved candidates.

**HANDOFF owns resumption:** reading order, environment prerequisites, state/milestone/decision/blocker references, runbooks, evidence access, cautions. Link `SESSION_SUMMARY.md#next-action`; keep state, completed-work lists, verification tables, and health scores with their owners. Preserve unique procedures here or link their existing runbook; relocate only within scope.

<a id="memory-update"></a>

### 11.3 Updates and evidence

Apply section 3's edit precautions. Update changed facts at their owner, then affected summary fields/references. Preserve IDs, history, and unrelated content; leave accurate files/timestamps unchanged.

State claims identify revision, environment, observation time, and evidence. Distinguish planned, implemented, committed, built, published, deployed, verified, and qualified; distinguish parent gitlinks, submodule HEADs, and uncommitted work where relevant. Attribute unverified prior claims to their source/date.

Use [verification reporting](#verification-results) and section 6's data rules. Link detailed evidence instead of copying output into memory. Inaccessible evidence remains a limitation or, when it prevents continuation, a blocker.

Health scoring requires a user request. Store it only in SESSION_SUMMARY with date, agreed rubric, evidence, and limitations. Unsupported categories are `NOT_ASSESSED`; incomplete assessments have no complete total. Scores do not qualify releases.

<a id="memory-checkpoint"></a>

### 11.4 Shared checkpoint workflow

For an explicit checkpoint/closeout, pause implementation. Limit work to memory maintenance, necessary read-only inspection, and documentation validation; section 4's restricted actions gain no authorization.

1. **Inspect:** Review relevant outcomes, memory sections, parent/affected nested-repository diffs, and evidence. Identify changed facts, unfinished work, and uncertainty.
2. **Record:** Assign changes to owners under 11.2; apply 11.3 within scope. Each affected record must be current or have a stated recording gap. Draft/review requests leave the repository untouched.
3. **Check consistency:** Match claims to sources, revision/image/version/environment/time identities, and state labels. Resolve links; require evidence for resolution/milestone claims; confirm one next action (or none assigned) and HANDOFF's reference. Correct introduced inconsistencies; report unresolved pre-existing contradictions. Preserve operational knowledge.
4. **Validate:** Check headings, links, anchors, fences, and tables; avoid escaped table-cell pipes. Run section 8's documentation check for repository edits or its draft checks for unapplied files. Record actual outcomes/reasons. Closeout does not authorize installing missing tools or expanding scope.
5. **Check recovery:** For closeout/handoff, apply 11.5; a checkpoint-only request skips this step.
6. **Report and stop:** State saved/draft/incomplete status, completed/unfinished work, changed documents, relevant decision/blocker changes, checks/results, the recorded next action or none assigned, and remaining gaps. Include readiness for closeout. Stop; executing the next action needs a subsequent user request.

Saving state does not complete the underlying task or qualify a release.

<a id="memory-closeout"></a>

### 11.5 Closeout readiness

Follow startup as a new agent without chat history. Verify that required records/references are usable and that local-only evidence has an access path or a documented limitation.

- **Usable:** Records support resumption; known blockers have documented resolution actions.
- **Limited:** Missing material affects later work; current state and immediate next action remain clear.
- **Incomplete:** Missing/conflicting information prevents determining current state or a safe next action.

Name gaps and effects. Review HANDOFF without forcing an edit; correct owned information within scope. Report unresolved gaps rather than inventing facts or starting implementation.
